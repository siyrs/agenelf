## 最小发布验收

在项目根目录执行。Linux/Docker 主机使用 `python3`；Windows 建议使用项目虚拟环境或
已安装的 Python 3.12。不要在带真实密钥的 `.env` 中记录或复制凭据。

```bash
cd app
python -m unittest discover -s tests -v
python -m compileall -q .
```

若改动涉及运行容器，额外验证：

```bash
bash scripts/sync_fork.sh
docker compose up -d --build
curl -fsS http://localhost:8000/health
curl -fsS http://localhost:8000/evolution/status
docker compose ps
```

`/health` 应返回 `status: ok`，`docker compose ps` 应显示服务处于运行状态。实际接入
模型时，另发起一次不含敏感信息的 `/chat` 请求，确认模型网关、工具调用和
`logs/audit.log` 的审计链路均符合预期。

## 安全回归重点

1. 对 `rm`、`chmod`、`kill`、`systemctl restart`、`pip install`、`curl | sh` 等命令，首次调用只能生成 `auth-*` 请求，不能执行。
2. 仅由宿主机执行 `bash scripts/approve.sh <ID> approve` 后，携带该 ID 的重试才能执行；授权必须一次性核销并在五分钟后过期。
3. Agent 的演进写入只能发生在 `app-tmp/`；`app/`、`app-fork/`、`scripts/` 和 `.env` 仍受挂载及 gate 双重约束。
4. 每次晋升前确认 `data/promote-requests/<ID>/report.txt` 没有 `[FAIL]`，且 `READY` 由 `gate_check.sh` 生成。

## 运行边界

- `server_ops` 是面向 Linux 服务器的工具。Windows 下 Git Bash 仅用于本地开发和测试兼容，不能替代对真实服务器的权限、网络与日志验证。
- 开发态 `evolution/engine.py` 依赖当前仓库有干净的 `main` 分支；生产自迭代应使用 Docker 中的 `evolution_ops → gate_check → promote` 三段流程。
- 记忆 JSON 保留完整历史；提示词限制只减少注入模型的内容，不会自动删除历史。若需要保留策略或语义检索，应以独立迁移实现，不能直接修改现有用户记忆文件。
